# 算法说明

本文档说明项目中的调度算法设计、当前实现状态，以及各算法的预期行为。

当前项目聚焦教学与演示，因此算法设计遵循两个原则：
- 先做容易理解、容易验证的基础算法。
- 如果算法体系继续扩展，尽量把“任务挑选”和“机器放置”分开考虑。

## 当前调度模型

当前仿真器采用的是简化模型：
- 所有任务先按 `submit_time` 进入等待状态。
- 当前版本默认按到达顺序处理等待中的任务。
- 调度器当前主要负责“把一个任务放到哪台机器上”。

也就是说，当前已经实现的算法本质上都是“机器放置策略”。

如果后续系统继续扩展，可以把调度拆成两层：
- 队列选择策略：决定下一个先尝试哪个任务。
- 机器放置策略：决定这个任务应该放到哪台机器。

## 已实现算法

## `first_fit`

### 核心思路
按照机器列表的固定顺序，从前往后扫描，找到第一台可以容纳当前任务的机器，就立即放置。

### 选择规则
- 机器必须处于启用状态。
- 机器剩余 CPU 必须大于等于任务所需 CPU。
- 机器剩余内存必须大于等于任务所需内存。
- 满足条件后，立即选择第一台符合要求的机器。

### 预期行为
- 逻辑最简单。
- 行为稳定，结果容易复现。
- 很适合做第一版基线算法。

### 优点
- 实现成本低。
- 易于讲解和调试。
- 调度开销小。

### 缺点
- 前面的机器更容易被优先填满。
- 容易出现负载不均衡。
- 当机器顺序固定时，结果会明显受机器排列顺序影响。

### 适用场景
- 教学演示。
- 作为其他算法的对照基线。
- 需要快速验证仿真链路时。

### 当前状态
- 已实现。
- 代码位置：`backend/app/schedulers/basic.py`

## `best_fit`

### 核心思路
在所有能容纳当前任务的机器中，优先选择“放进去之后最紧凑”的那台机器。

当前实现中，主要按任务放入后剩余 CPU 最少来选择候选机器。

### 选择规则
- 先筛掉无法容纳任务的机器。
- 在可用候选中，选择 `available_cpu - task.required_cpu` 最小的机器。

### 预期行为
- 更倾向于把任务压缩到少数机器中。
- 可能保留大机器给后续更大的任务。
- 资源使用看起来会更“紧凑”。

### 优点
- 在部分负载下能提高资源利用率。
- 便于展示“装箱”思路。
- 可能减少机器资源的粗放浪费。

### 缺点
- 只按 CPU 余量做判断时，未必能同时兼顾内存碎片。
- 有时会把某些机器塞得太满，降低后续灵活性。
- 负载变化较大时，可能产生新的局部碎片。

### 适用场景
- 想演示“紧凑放置”思想时。
- 任务规模差异明显，希望优先保留大容量机器时。

### 当前状态
- 已实现。
- 当前是 CPU 优先的简化 `best fit`，不是 CPU+内存联合评分版本。
- 代码位置：`backend/app/schedulers/basic.py`

## `worst_fit`

### 核心思路
在所有能容纳当前任务的机器中，优先选择“放进去之后仍然最宽松”的那台机器。

当前实现中，主要按任务放入后剩余 CPU 最多来选择候选机器。

### 选择规则
- 先筛掉无法容纳任务的机器。
- 在可用候选中，选择 `available_cpu - task.required_cpu` 最大的机器。

### 预期行为
- 更倾向于把任务分散到多台机器。
- 某些情况下可以改善局部过热问题。
- 与 `best_fit` 形成明确对照。

### 优点
- 有助于展示“分散负载”的思路。
- 相对不容易把前几台机器迅速塞满。
- 在部分场景下更容易得到较均匀的资源占用。

### 缺点
- 可能让小任务过早占用大机器。
- 可能降低整体装箱紧凑度。
- 对后续大任务未必友好。

### 适用场景
- 想展示“均摊式放置”与“紧凑式放置”的差异时。
- 做对比实验时。

### 当前状态
- 已实现。
- 当前是 CPU 优先的简化 `worst fit`。
- 代码位置：`backend/app/schedulers/basic.py`

## `round_robin`

### 核心思路
不总是从第一台机器开始扫描，而是维护一个轮转指针，从上次成功放置后的下一台机器开始尝试。

### 选择规则
- 调度器保存一个内部下标 `next_index`。
- 每次从 `next_index` 开始循环扫描机器列表。
- 找到第一台能容纳任务的机器后完成分配。
- 下一次调度从这台机器的下一台继续开始。

### 预期行为
- 避免每次都偏向列表前部机器。
- 让机器获得更平均的“被优先尝试”机会。
- 非常适合做公平性直觉演示。

### 优点
- 容易理解。
- 比 `first_fit` 更不依赖固定起点。
- 有助于教学中说明“轮转公平性”的概念。

### 缺点
- 轮转公平不等于资源利用最优。
- 如果机器能力差异较大，简单轮转可能不够聪明。
- 仍然需要满足资源容量约束，不能保证一定更均衡。

### 适用场景
- 需要展示简单公平思想时。
- 作为 `first_fit` 的对照算法。

### 当前状态
- 已实现。
- 代码位置：`backend/app/schedulers/basic.py`

## 已规划算法

下面这些算法已经进入项目规划，但当前版本还没有实现。文档先说明它们的目标与预期行为，后续实现时可以据此落地。

## `cfs_like`

### 类型
- 简化的任务选择策略，结合基础机器放置策略。

### 核心思路
参考 Linux CFS（Completely Fair Scheduler）的公平调度思想，在等待队列中优先选择“估算虚拟运行时间”更小的任务。

当前项目中的 `cfs_like` 是教学用简化版，不实现真正的时间片抢占，而是先对等待任务做排序，再复用基础的机器放置逻辑。

### 当前简化规则
- 估算虚拟运行时间使用：`duration / (priority + 1)`
- 值越小，越优先被调度
- 如果估算值相同，则按 `submit_time` 和 `id` 排序
- 任务选出后，机器放置仍使用从前往后的可放置扫描

### 预期行为
- 较短任务、较高优先级任务会更早获得运行机会
- 相比单纯先来先服务，更强调一种“近似公平且响应更快”的效果

### 优点
- 保留了“虚拟运行时间”这个核心教学概念
- 不需要把当前仿真器改造成真正可抢占调度器
- 可以直接接入现有架构

### 缺点
- 这不是 Linux CFS 的完整实现
- 当前更接近“基于简化虚拟运行时间的等待队列排序”
- 机器放置部分仍然是简单扫描，不包含复杂负载均衡

### 当前状态
- 已实现。
- 适合作为 Linux 调度思想的入门演示版本。

## `least_loaded`

### 类型
- 机器放置策略。

### 核心思路
优先把任务放到当前负载最低的机器上。

### 当前实现规则
- 先筛出所有可以容纳任务的机器。
- 按当前 CPU 利用率从低到高排序。
- 如果 CPU 利用率相同，再按当前内存利用率从低到高排序。
- 如果仍然相同，再按 `id` 保持稳定顺序。

### 预期行为
- 更贴近“负载均衡”直觉。
- 可以借鉴 Linux 多核负载均衡思想。
- 相比 `round_robin`，它是按当前状态自适应决策，而不是机械轮转。

### 优点
- 容易解释。
- 更强调集群均衡。
- 在资源分布不均时可能优于轮转。

### 缺点
- 需要定义“负载”的计算方式。
- 如果只看 CPU，可能忽略内存瓶颈。
- 过度追求均衡时，未必能得到最紧凑的装箱效果。

### 当前状态
- 已实现。
- 当前版本使用“CPU 利用率优先，内存利用率次之”的简化负载定义。
- 代码位置：`backend/app/schedulers/basic.py`

## `priority`

### 类型
- 队列选择策略。

### 核心思路
等待队列中优先选择优先级更高的任务，再尝试放置。

### 可能的实现方式
- 按 `priority` 从高到低排序。
- 同优先级下再按 `submit_time` 保持先来先服务。

### 预期行为
- 高优先级任务更早被调度。
- 适合演示业务优先级影响。

### 优点
- 易于理解。
- 与任务字段天然匹配。

### 缺点
- 低优先级任务可能被长期推迟。
- 需要设计是否允许“老化”机制防止饥饿。

### 当前状态
- 已规划，未实现。

## `sjf`

### 类型
- 队列选择策略。

### 核心思路
SJF 是 Shortest Job First，优先调度运行时间较短的任务。

### 可能的实现方式
- 按 `duration` 从小到大排序。
- 同时结合机器可放置性决定是否真正启动。

### 预期行为
- 通常有助于降低平均等待时间。
- 会更快完成一批短任务。

### 优点
- 教学中非常经典。
- 与等待时间、周转时间等指标关系直观。

### 缺点
- 长任务可能被持续推迟。
- 在真实系统中往往需要预估运行时间，教学模型中虽然有 `duration`，但现实里不一定已知。

### 当前状态
- 已规划，未实现。

## `edf`

### 类型
- 队列选择策略。

### 核心思路
EDF 是 Earliest Deadline First，优先调度截止时间最早的任务。

### 可能的实现方式
- 按 `deadline` 从小到大排序。
- 没有截止时间的任务可以放在后面，或者视为无穷大。

### 预期行为
- 更适合展示实时性约束。
- 当任务有时间目标时，比单纯先来先服务更合理。

### 优点
- 与 `deadline` 字段直接对应。
- 适合作为“实时调度思想”的入门示例。

### 缺点
- 不保证高资源占用任务一定能及时放下。
- 只考虑截止时间时，可能牺牲其他整体指标。

### 当前状态
- 已规划，未实现。

## `balanced`

### 类型
- 机器放置策略。

### 核心思路
综合 CPU 和内存两个维度，尽量把任务放到能让整体资源更平衡的机器上。

### 可能的实现方式
- 定义一个综合评分函数。
- 例如同时考虑放置后的 CPU 利用率和内存利用率差异。
- 选择综合分数最优的机器。

### 预期行为
- 比只看 CPU 的 `best_fit` / `worst_fit` 更贴近当前项目的双资源模型。

### 优点
- 更符合本项目“CPU + 内存”双资源现实。
- 教学上可以引出多维资源调度问题。

### 缺点
- 评分函数设计会明显影响结果。
- 比基础算法更难解释和验证。

### 当前状态
- 已规划，未实现。

## `quota_aware`

### 类型
- 机器放置策略，或与任务选择联动的扩展策略。

### 核心思路
参考 Linux cgroups 的资源配额思想，在调度时考虑任务或任务组的资源上限、保底或配额约束。

### 可能的实现方式
- 给任务增加额外配额信息。
- 调度时除了看机器是否能放下，还要看是否满足配额规则。

### 预期行为
- 更适合演示“资源隔离”和“资源治理”概念。
- 可以作为从单机 OS 资源控制迁移到云调度的桥梁。

### 优点
- 有明确系统设计背景。
- 能拓展项目的教学深度。

### 缺点
- 超出当前 MVP 范围。
- 需要新增更多数据字段和约束规则。
- 如果没有任务组、多租户或配额概念，算法很难完整发挥作用。

### 当前状态
- 已规划，未实现。

## 推荐的实现顺序

如果后续继续实现扩展算法，建议顺序如下：

1. `least_loaded`
2. `priority`
3. `sjf`
4. `edf`
5. `balanced`
6. `cfs_like`
7. `quota_aware`

原因是：
- `least_loaded` 最接近当前架构，只需扩展机器选择逻辑。
- `priority`、`sjf`、`edf` 主要影响队列选择，教学价值高，逻辑也清楚。
- `balanced` 需要先想清楚双资源评分方法。
- `cfs_like` 和 `quota_aware` 概念更强，但实现复杂度更高。

## 教学对比建议

如果用于课程、演示或报告，建议做以下几组对比：

1. `first_fit` vs `round_robin`
对比固定起点扫描与轮转公平。

2. `best_fit` vs `worst_fit`
对比紧凑装箱与分散放置。

3. `first_fit` vs `least_loaded`
对比简单规则与负载感知规则。

4. `sjf` vs `priority` vs `edf`
对比不同任务选择策略对等待时间、成功率、截止时间满足率的影响。

## 注意事项

- 当前代码中已经可调用的算法有：`first_fit`、`best_fit`、`worst_fit`、`round_robin`、`least_loaded`、`cfs_like`。
- 文档中的其他算法目前属于设计说明，不应在 API 或前端中提前暴露为可运行选项。
- 当前实现对 `best_fit` 和 `worst_fit` 的判断主要基于 CPU 余量，后续如果扩展为双资源评分，应同步更新本文档。
